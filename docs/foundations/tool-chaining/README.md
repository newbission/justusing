# 도구 넘기기 (tool chaining)

쓴 날 2026-10-24 · 고친 날 2026-10-24

- 쓰는 곳: 결과를 다른 도구로 바로 넘길 수 있는 도구 (아래 "넘길 수 있는 쌍")
- 상태: PR 진행 중 (`feat/tool-chaining`)
- 관련 문서: [히스토리](./history.md), [격리 frame](../frame-isolation/README.md), [사이트 구조](../site-structure/README.md),
  [글꼴·데이터 보관](../fonts-and-data/README.md)

## 1. 어떤 기반인지

도구 결과를 내려받았다가 다시 올리지 않고 다음 도구로 바로 넘긴다. 예: 배경을 지운 사진을 증명사진 만들기로,
자른 사진 여러 장을 이미지를 PDF로.

- 결과 화면의 실행 막대(`ActionBar`)에 **'다음 도구로'** 버튼이 있다. 누르면 넘길 수 있는 도구 목록이 뜬다
- 고르면 도구 칸(격리 frame) 안의 화면이 그 도구로 바뀌고, 결과 파일이 **놓은 파일처럼** 들어가 첫 화면(파일 고르기)을 건너뛴다
- 바깥 페이지는 주소(`/image/id-photo/`)·제목·쓰임새·사용법·FAQ·관련 글을 그 도구 것으로 바꾼다. 광고 칸과 도구 칸은 그 자리 그대로다
- 넘긴 파일 이름은 원래 이름 그대로다 (`portrait_배경제거.png`). 이름도 바이트도 도구 칸 밖으로 나가지 않는다

하지 않는 것·한계

- 넘길 수 있는 쌍은 레지스트리에 선언한 것뿐이다 (아래). 동영상 도구로는 넘기지 않는다 (CSP, 아래 "넘기지 않는 쌍")
- 뒤로 가기는 앞 도구 페이지를 **새로** 연다. 앞 도구에서 하던 것과 넘긴 파일은 남지 않는다 (보통 페이지 이동과 같다)
- '예시로 따라 하기' 창 안에서는 넘기지 않는다 (창은 견본으로 사용법만 보여 준다)
- 개발 서버(`npm run dev`)에서는 빌드 목록(`/_chain/`)이 없어 다음 도구 페이지를 읽어 불러온다. 격리·CSP가 꺼져 있으므로 실제 동작은 빌드 결과로 확인한다

## 2. 설계: 후보와 고른 것

### 절대 조건

1. 파일 바이트와 파일 이름이 **바깥 페이지의 JS 문맥**(광고·통계가 도는 곳), 주소, 저장소, 네트워크에 닿지 않는다.
   바깥이 '전달'만 해도 그 페이지의 다른 스크립트가 가로챌 수 있다. 바깥이 끼어드는 키 교환도 능동적 가로채기에 약하다
2. sandbox(`allow-scripts allow-downloads`, allow-same-origin·allow-popups·allow-forms 없음), frame CSP, 페이지별 CSP 해시를 넓히지 않는다
3. 성능 철칙: 바깥 페이지와 각 도구 frame 첫 화면이 무거워지지 않는다

### 파일을 어떻게 넘기나 (후보 비교)

| 후보                                                                         | 판단                                                                                                                                                                           |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **A. 같은 frame 문서 안에서 화면만 다음 도구로 바꾸기**                      | **채택.** 파일은 frame의 메모리(`File` 객체)에서 다음 도구 화면으로 옮겨질 뿐 어떤 메시지·저장소·주소에도 실리지 않는다. 바깥은 내용 없는 `tool-change` 신호(도구 ID)만 받는다 |
| B. 바깥 페이지를 거쳐 `postMessage`로 다음 frame에 전달                      | 금지. 바이트가 바깥 문맥의 `message` 이벤트로 들어온다. 광고 스크립트가 같은 창에서 듣거나 `postMessage`를 감싸면 읽힌다                                                       |
| C. 바깥이 만든 `MessageChannel`의 포트를 두 frame에 나눠 주기                | 금지. 포트를 만든 쪽(바깥)이 포트를 바꿔치기하거나 하나를 몰래 가질 수 있다. 키 교환을 더해도 바깥이 가운데에 끼면(능동 가로채기) 막을 수 없다                                 |
| D. frame끼리 직접 `postMessage` (`parent.frames[i]`)                         | 금지. 출처가 `null`이라 받는 쪽 출처를 지정할 수 없고(`'*'`), 바깥(조상)은 형제 frame을 아무 때나 자기 문서로 이동시킬 수 있다. 보내는 순간 가로챌 수 있다                     |
| E. frame 안에 다음 도구 frame을 하나 더 띄우기 (중첩)                        | 금지. HTML 규칙상 최상위 페이지는 손자 frame도 이동시킬 수 있어 D와 같다. 화면·CSS·메모리도 두 벌                                                                              |
| F. frame 주소를 다음 도구로 옮기고 `window.name`에 실어 가기                 | 금지. `window.name`은 같은 창이 다른 문서로 바뀌어도 남는다. 바깥이 frame을 자기 페이지로 옮기면 읽힌다. 문자열이라 큰 파일에 맞지도 않는다                                    |
| G. frame 저장소(IndexedDB·Cache)·`BroadcastChannel`에 두었다가 다음 문서에서 | 불가. 출처 `null` 문서는 저장소를 쓸 수 없고, 문서마다 새 출처라 `BroadcastChannel`도 닿지 않는다 (그리고 저장소에 남기는 것 자체가 조건 위반)                                 |
| H. 지금처럼 내려받고 다시 고르기                                             | 안전하지만 불편하다. 넘기기가 실패하거나 넘길 수 없는 쌍에서는 그대로 이 방법이 남는다                                                                                         |

### 다음 도구의 코드·CSS를 어떻게 불러오나

| 후보                                                                                                        | 판단                                                                                                                                                                                                                                                                                                                                   |
| ----------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| a. 앞 도구 코드에 `import('../id-photo/App.svelte')`                                                        | 버림. Astro는 페이지 스크립트에서 **동적 import로 닿는 모듈의 CSS까지** 그 페이지 `<link>`에 넣는다 (`astro/dist/core/build/graph.js`가 `dynamicImporters`도 따라 올라간다. 지금 배경 제거의 `Workspace.css`가 첫 화면에 실린 것으로 확인). 넘길 도구들의 CSS가 앞 도구 첫 화면에 붙어 성능 철칙을 어긴다                              |
| b. Astro 내부 표식(`?astroPropagatedAssets`)으로 CSS 따라가기를 끊기                                        | 버림. Astro 내부 구현에 기대 업그레이드 때 조용히 깨질 수 있고, `App.svelte`를 두 번 컴파일한다                                                                                                                                                                                                                                        |
| c. 실행 중에 다음 도구 frame HTML을 받아 그 안의 스크립트·CSS를 불러오기                                    | 그대로는 안 된다. frame HTML에는 CORS가 없고, 작은 CSS는 인라인 `<style>`로 들어 있는데 이 문서 CSP의 해시는 앞 도구 것뿐이라 막힌다                                                                                                                                                                                                   |
| **d. 빌드 뒤 다음 도구의 자료 목록을 만들어 두고, 그 도구 자신의 frame 진입 스크립트를 실행 중에 불러오기** | **채택.** 빌드가 끝나면(`astro:build:done`) 받는 쪽 도구마다 frame 페이지가 부르는 스크립트·CSS 주소와 인라인 `<style>`(파일로 뺀 것)을 `/_chain/<id>.json`에 적는다. 넘길 때만 frame이 이 목록을 받아 `<link rel="stylesheet">`를 넣고 진입 스크립트를 `import()`한다. 우리 사이트 파일이라 지금 CSP(`'self'` + 사이트 주소)로 열린다 |

- 진입 스크립트는 그 도구의 `Frame.astro` 스크립트다. 모든 `Frame.astro`가 `mount()` 대신 `startTool(App)`(`src/frame/mount.ts`)을 부르게 바꿨다.
  처음 열린 페이지에서는 바로 띄우고, 넘기는 중에 불렸으면 띄우지 않고 App만 넘긴다. 그래서 다음 도구 코드를 **다 받은 뒤에** 앞 화면을 내린다
  (받다가 실패하면 앞 화면이 그대로 남는다)
- 같은 문서이므로 공통 모듈(Svelte 실행 코드, `drop.ts`, `mount.ts` …)은 이미 받은 것을 그대로 쓴다. 다시 받는 것은 그 도구에만 있는 파일뿐이다

### 바깥 페이지는 무엇을 하나

| 후보                                                               | 판단                                                                                                                        |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| 아무것도 바꾸지 않기                                               | 버림. 주소·제목·사용법·FAQ가 앞 도구 그대로라 헷갈리고, 새로고침·공유하면 앞 도구가 열린다                                  |
| 주소를 다음 도구로 옮겨 새로 불러오기                              | 불가. frame이 다시 떠 넘긴 파일이 사라진다                                                                                  |
| **`history.pushState` + 다음 도구 페이지를 받아 글 부분만 바꾸기** | **채택.** 도구 칸(iframe)과 광고 칸은 DOM에서 옮기지 않는다 (iframe을 옮기면 다시 불러와 파일을 잃고, 광고는 다시 그려진다) |

바깥이 받는 신호는 `{ type: 'tool-change', tool: 'image/id-photo' }`뿐이다. 바깥은

1. `event.source`가 그 도구 frame인지, 도구 ID 모양(`/^[a-z]+\/[a-z0-9-]+$/`)인지 본다
2. 다음 도구 페이지(`/image/id-photo/`, 영어는 `/en/...`)를 받아 `[data-swap]` 구역(머리·쓰임새와 사용법·FAQ·관련 글)을 바꾸고,
   `<title>`·설명·canonical·hreflang·OG, 머리글의 언어 바꾸기 링크와 메뉴의 '지금 페이지' 표시, iframe `title`을 맞춘다
3. 바꾸기 전후의 도구 칸 위치 차이만큼 바로 스크롤해 도구 칸이 화면에서 움직이지 않게 한다 (CLS)
4. `pushState`로 주소를 바꾼다

받는 것은 우리 공개 페이지(파일 정보 없음)뿐이다. 바깥에서 하는 일은 모두 넘기기가 **끝난 뒤** 일어나고, 실패해도 도구 칸은 이미 다음 도구로 바뀌어 있다
(바깥은 그대로 남는다). 이 코드는 신호가 올 때만 받는다 (`src/lib/tool-switch.ts`, 첫 화면 무게에 들지 않음).

### 확인한 것

- **CSP 차이**: 동영상 카테고리 frame만 `media-src blob:`가 있다. frame CSP는 문서를 열 때 정해져 바꿀 수 없으므로, 넘긴 도구는 **처음 연 frame의 CSP**로 돈다.
  빌드가 넘길 수 있는 모든 경로(여러 번 넘기기 포함)에서 받는 도구 frame의 CSP 값(해시 말고)이 처음 frame CSP 안에 드는지 확인하고, 아니면 멈춘다.
  동영상 장면 캡처 → 이미지 도구는 처음 frame이 더 넓을 뿐(`media-src blob:`)이라 된다. 이미지 → 동영상은 안 된다
- **CSS·JS 불러오기와 Safari**: 다음 도구의 파일은 `/_astro/`·`/_chain/` 아래 우리 파일이고, frame CSP는 `'self'`와 사이트 주소(Safari 규칙)로 이미 허용한다.
  `<link>`는 스크립트로 넣은 요소라 인라인이 아니다(해시 불필요). 인라인 `<style>`은 빌드가 `/_chain/<id>.<해시>.css`로 빼 두어 실행 중에 `<style>`을 만들지 않는다.
  모듈 `import()`와 목록 `fetch()`는 출처 null 요청이라 `_headers`에서 `/_chain/*`에 CORS를 열었다 (`/_astro/*`는 이미 열려 있음)
- **CLS**: 도구 칸과 광고 칸은 DOM에서 옮기지 않는다. 바꾸는 구역은 도구 칸 위(머리)와 아래(본문)뿐이고, 머리 높이가 달라진 만큼 같은 순간에 스크롤을 고쳐
  도구 칸이 화면에서 움직이지 않는다. `below-tool` 칸은 늘 같은 안내 문구 바로 아래라 도구 칸과 함께 그대로다. frame 안의 높이는 그대로(칸 높이 고정)
- **뒤로 가기**: `pushState` 하나를 쌓는다. 뒤로 가면(`popstate`, 경로가 다를 때만) 그 주소를 새로 연다 → 앞 도구 첫 화면. 앞으로 가기도 같다.
  같은 페이지 안의 `#` 이동은 경로가 같아 다시 열지 않는다
- **접근성**: 다음 도구로 바뀌면 frame 안 알림(`role="status"`, 바꾸기 전부터 있는 칸)이 "증명사진 만들기로 사진 1장을 넘겼습니다"를 읽고, 포커스를 도구 화면(`#app`)으로 옮긴다.
  frame 문서 제목과 iframe `title`, 바깥 `<title>`·`h1`도 바뀐다. 메뉴는 버튼(`aria-expanded`) + 목록, 화살표·Home·End로 옮기고 Esc로 닫으면 버튼으로 돌아간다
- **데이터 받기 동의**: 넘긴 뒤에도 그 도구가 평소처럼 묻는다 (증명사진의 얼굴 찾기 데이터, 배경 제거 모델). 넘긴다고 저절로 받지 않는다
- **영어 주소**: 신호에는 도구 ID만 있고, 바깥이 자기 언어로 주소를 만든다 (`/en/image/id-photo/`). frame은 `<html lang>`이 같아 같은 언어로 그린다
- **이름**: 넘기는 파일 이름은 그 도구가 내려받을 때와 같다. frame 안의 화면에만 보이고, 바깥 신호·주소·제목에는 없다 (E2E가 바깥 문맥을 감시해 확인)
- **메모리**: 앞 화면을 내리면(`unmount`) 그 도구의 정리 코드가 워커·그림을 놓는다. 원본을 워커에 들고 있는 자르기·모자이크는 화면을 내릴 때 워커를 끝내게 고쳤다

### 넘기지 않는 쌍 (이유)

- **이미지·PDF 도구 → 동영상 도구**: 동영상 frame만 `media-src blob:`가 있다. 이미지 frame에서 연 문서는 그 CSP를 늘릴 수 없다 (넓히는 것도 조건 위반). 빌드가 막는다
- **동영상 → 동영상** (자르기 → 용량 줄이기 등): CSP는 같아 될 수 있지만 수백 MB 결과를 메모리에 두 번 들 수 있어 이번에는 하지 않는다 (메모리 측정 뒤에)
- **따라 하기 창 안**: 견본으로 사용법만 보여 주는 창이라 넘기기 버튼을 그리지 않는다
- **여러 장 결과 → 한 장만 받는 도구**(증명사진·자르기·모자이크): 어느 장인지 알 수 없어 목록에서 흐리게 두고 "한 장일 때만"이라고 알린다

| `image/resize`        | `pdf/from-image`                                                      |

- 보내는 도구 `meta.ts`: `sendTo: ['image/id-photo', ...]`

- 레지스트리가 빌드 때 확인한다: 받는 도구가 있고 live이고 `receives`가 있는지, 자기 자신이 아닌지
- 빌드 뒤 `tool-chain` 통합이 확인한다: 넘길 수 있는 모든 경로에서 CSP가 처음 frame 안에 드는지, 받는 도구 frame의 인라인 스크립트가 처음 frame에도 있는지
