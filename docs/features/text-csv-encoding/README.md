## 1. 어떤 기능인지

- 엑셀에서 CSV를 열면 한글이 깨지는 문제를 고친다. 흔한 두 경우:
  - BOM 없는 UTF-8 CSV(웹 서비스가 내보낸 것)를 한국어 윈도우 엑셀에서 열면 CP949로 읽혀 `媛쒖씤`처럼 나온다
  - CP949(EUC-KR) CSV(은행·관공서·예전 프로그램)를 UTF-8로 읽는 곳(구글 시트·Numbers)에서 열면 `�`로 나온다
- 입력: `.csv`·`.tsv`·`.txt`(또는 `text/csv`·`text/plain` 형식) 여러 개. 수백 MB도 된다 (397MB 파일 5초, 2026-10-23 크롬)
- 파일마다 원래 인코딩을 알아내고, 앞부분(64KB에서 6줄·8칸)을 엑셀처럼 칸 이름·줄 번호를 단 표 둘로 보여 준다
  - 위 표: 지금 열리는 모습. 원본이 엑셀 기본 인코딩(한국어 화면 CP949, 영어 화면 Windows-1252)이면 'UTF-8로 읽는 곳',
    아니면 '지금 엑셀에서 열면'. BOM이 있으면 엑셀도 그것을 따르므로 표 하나와 '이미 엑셀에서 바로 열린다' 안내
  - 아래 표: 바꾼 뒤 (고른 원본 인코딩으로 읽은 것, CP949로 저장하면 없는 글자는 `?`)
  - 맞지 않으면 원본 인코딩을 직접 고른다: UTF-8, CP949, UTF-16 LE/BE, Windows-1252, Shift_JIS, GBK, Big5
- 저장 형식: 엑셀용 UTF-8(BOM 포함, 기본) / UTF-8(BOM 없음) / CP949. 줄바꿈: 그대로(기본) / CRLF / LF
- 출력: `<이름>_엑셀용.csv`(영어 `_excel`), `_UTF8`, `_CP949`. 원래 확장자(csv·tsv·txt)를 지킨다.
  여러 개는 `CSV_인코딩변환.zip`(영어 `converted-csv.zip`). 이미 고른 형식인 파일은 바꾸지 않고 원본을 ZIP에 넣는다
- 하지 않는 것·한계
  - 글자·쉼표·따옴표는 그대로 둔다. CSV를 해석해 다시 쓰지 않는다 (미리보기만 해석한다)
  - CP949에 없는 글자(이모지, 많은 외국 글자)는 `?`로 바꾼다. 개수와 처음 5개의 글자·줄 번호를 알린다
  - 원본 인코딩으로 읽지 못한 바이트는 `�`가 된다. 미리보기와 목록에 알린다
  - 자동 판단은 UTF-8·UTF-16·CP949·Windows-1252만 한다. Shift_JIS 등은 직접 고른다 (일본어 Shift_JIS는 CP949로 읽혀도
    깨지지 않는 바이트가 많아 자동으로 가르기 어렵다)
  - 엑셀이 숫자로 바꾸는 문제(앞자리 0)는 인코딩과 별개라 고치지 않는다 (가이드에 엑셀 가져오기로 푸는 법을 적음)

### 처리 흐름

1. 파일을 넣으면 워커가 앞부분을 1MB씩 읽는다. ASCII가 아닌 바이트가 4,096개 보이거나 끝(또는 32MB)까지 읽으면 판단한다
2. 판단 순서: 빈 파일 → BOM(UTF-8·UTF-16) → BOM 없는 UTF-16(0 바이트가 짝·홀 한쪽에 몰림) → 글자 파일 아님(NUL, 조절 문자 2% 넘음)
   → ASCII만(파일 전체를 읽었을 때만) → UTF-8(fatal 디코더로 깨짐 없음) → CP949(깨짐 없고 한글 완성형이 ASCII 밖 글자의 30% 이상)
   → Windows-1252
3. 화면은 받은 앞부분 64KB로 미리보기 표를 만든다 (TextDecoder, 칸 나눔은 TSV면 탭, 아니면 첫 줄에 많은 쉼표·탭·세미콜론)
4. 변환하기: 파일마다 차례로 워커가 `file.stream()`을 읽어 `TextDecoder(stream)` → 줄바꿈 → UTF-8(`TextEncoder`)이나 CP949(표)로 쓰고,
   조각들을 `Blob` 하나로 모아 넘긴다. 1%마다 진행률을 보낸다
5. 이미 고른 형식(같은 인코딩·BOM, 줄바꿈 그대로)이면 워커를 거치지 않고 '원본 그대로'로 둔다

### 결정과 이유

- **카테고리 주소를 `text`로** (2026-10-23): 처음에 `data`로 만들었다가 `/data/`가 글꼴·OCR 데이터 파일 자리(`public/data/`,
  `data-store.ts`가 `/data/`로 시작하는 주소만 보관)와 겹쳐 바꿨다. `categories.ts` 주석에 겹치면 안 되는 주소를 적었다
- **CP949 쓰기 표를 실행 중에 만든다**: 브라우저에는 UTF-8 인코더만 있다. 표(약 1만7천 자)를 코드에 넣으면 수십 KB가 늘어
  `TextDecoder('euc-kr')`(WHATWG 표준, CP949 확장 완성형 전체)로 모든 두 바이트를 한 번 읽어 거꾸로 표를 만든다 (수 ms).
  두 바이트마다 LF를 끼워 한 줄에 한 글자씩 읽는다. 없는 자리는 `�`나 두 글자(뒤 바이트가 ASCII면 되돌려짐)로 나와 빠진다
- **기본 저장 형식은 엑셀용 UTF-8(BOM)**: 엑셀·구글 시트·Numbers 모두에서 열린다. BOM 없는 UTF-8은 업로드·코드용으로 둔다
- **위 표는 '엑셀에서 열면'과 'UTF-8로 읽는 곳에서 열면' 중 하나**: CP949 파일은 한국어 엑셀에서는 멀쩡하므로, 엑셀 모습을 보이면
  "깨지지 않았는데?"가 된다. 원본이 엑셀 기본 인코딩이면 그 파일이 깨지는 곳(UTF-8로 읽는 곳)을 보인다
- **CSV를 해석해 다시 쓰지 않는다**: 바이트 → 글자 → 바이트만 한다. 따옴표·빈 칸·줄 끝 공백을 바꿀 위험이 없다
- **결과를 Blob으로**: 수백 MB를 `Uint8Array` 하나로 모으면 메모리를 두 번 쓴다. ZIP으로 받을 때만 바이트로 읽는다
- **E2E 기준 파일은 파이썬 코덱으로**: 도구의 인코더로 만든 기준은 같은 실수를 놓친다. Node의 `TextDecoder('euc-kr')`는
  확장 완성형(똠)을 못 읽어서, CP949 결과 확인은 브라우저의 디코더로 한다

### 주의할 점

- 원본 인코딩 고르기는 `<select>`다. 격리 frame 규칙(`style` 속성 금지, `<form>` 금지)을 지킨다
- 줄바꿈 바꾸기는 조각 끝의 CR을 다음 조각까지 남겨 둔다 (CRLF가 조각 경계에 걸리면 줄이 둘로 늘어난다). E2E가 6MB 파일로 확인한다
- 원본 인코딩·저장 형식·줄바꿈을 바꾸면 그 파일의 결과를 버린다 (결과마다 설정 키를 둔다)
- 버튼 이름을 바꾸면 `content.ts`의 사용법과 가이드(`fix-csv-encoding`)도 같이 고친다 (따라 하기가 따옴표 속 이름으로 버튼을 찾는다)

## 4. 검증

### 자동 테스트

- `tests/e2e/text-csv-encoding.spec.ts`
  - CP949 CSV → 엑셀용 UTF-8: 바이트가 BOM + 파이썬이 만든 글자의 UTF-8과 같다, 'UTF-8로 읽는 곳' 표와 바꾼 뒤 칸
  - BOM 없는 UTF-8 판별, '지금 엑셀에서 열면', 같은 형식이면 '원본 그대로'(받기 없음), 엑셀용은 BOM만 붙는다
  - Shift_JIS 파일: 자동이 맞히지 못하고, 직접 고르면 일본어가 보이고 CRLF로 바꾼 결과가 바이트 그대로
  - CP949로 저장: 미리보기에 `?`, 없는 글자 1개 안내와 글자·줄 번호, 확장 완성형 바이트(똠 8C63, 펲 BC84), 브라우저로 다시 읽은 글자
  - 여러 파일 ZIP: 바꾼 파일과 이미 맞는 파일(원본)
  - 6MB CP949 파일을 LF로: 조각 경계에서 글자·줄바꿈이 맞다
  - 빈 파일·이미지(.csv 이름)는 빼고 알린다, PDF는 받지 않는다
  - 영어 화면: Windows-1252 판별과 영어 안내, `_excel` 이름
- `tests/e2e/samples.spec.ts`: 견본 두 개가 들어간다 (모든 도구 공통)
